# Дорожная карта — перенос под клиента Комарова

Это **не разработка с нуля**, а перенос готовой системы автопостинга (проект AlexNef,
`Downloads/ЗАКАЗЫ/posting_vk/vkposter`) под второго клиента. Код продукта уже написан и
проверен на проде: 14 этапов исходной разработки описаны в
[`07_ROADMAP_PRODUCT.md`](07_ROADMAP_PRODUCT.md) — этот файл читать как справочник
по устройству системы, чекбоксы там относятся к первому клиенту и здесь не действуют.

Что реально меняется при переносе:

1. **Другой сервер.** Первый клиент живёт на выделенном VPS со своим Postgres и своим
   Caddy. Этот проект подселяется на общий сервер okhost (`193.17.95.54`), где Postgres,
   Redis и Caddy — общие на всех клиентов. Значит: свой `postgres` из compose убрать,
   подключение брать из `.env.infra`, порты наружу не публиковать, задать `mem_limit`.
2. **Другие ключи и другой проект в postmypost** (`project_id 345029`), другие группы —
   9–10 в ВК плюс Одноклассники.
3. **Четыре новых источника** сверх шести имеющихся. Два берутся картой сайта, двум
   нужны свои адаптеры (карта пустая / структура нестандартная).
4. **Другой домен** — `vktop545.com`.

> **Где смотреть прогресс**: [`STATUS.md`](STATUS.md). Внутри каждого этапа ниже —
> чекбоксы acceptance-пунктов. Закрытие этапа сопровождается тегом `stage-N-done`.
>
> **Правило**: за один заход — один этап. Человек верифицирует его вживую, только после
> этого ставится тег и берётся следующий.

## Этап 1 — Адаптация под общий сервер okhost

**Цель**: проект соответствует правилам общего сервера — не поднимает свою БД, не
публикует порты, знает свой потолок памяти.

**Что делаем**:
- Из `docker-compose.yml` убрать сервис `postgres` и `depends_on` на него; из
  `docker-compose.prod.yml` — сервис `caddy` и публикацию портов (и то и другое общее).
- Подключение к БД: поддержать `DATABASE_URL` в `src/config.js` и `src/db/pool.js`
  (okhost выдаёт именно его в `.env.infra`), оставив старые `POSTGRES_*` как запасной путь
  для локальной разработки.
- Контейнер назвать `komarov-vkposter-app` — на это имя ссылается общий Caddy.
- `mem_limit` и `cpus` на сервис; сети `data` (БД) и `edge` (HTTP от Caddy) как external.
- `.github/workflows/deploy.yml` переписать под okhost: `INSTALL_DIR`,
  `docker compose up -d --build` одним файлом (продового слоя с Caddy больше нет).

**Критерии приёмки** (закрытие → tag `stage-1-done`):
- [ ] В `docker-compose.yml` нет сервисов `postgres`, `redis` и ни одного `ports:`
- [ ] У сервиса `app` заданы `container_name: komarov-vkposter-app`, `mem_limit`, `cpus`
- [ ] Приложение стартует, когда подключение задано только через `DATABASE_URL`
- [ ] Локальный запуск (со своим Postgres через override) по-прежнему работает

## Этап 4 — Новые источники по карте сайта

**Цель**: два новых сайта дают материал штатным механизмом, без своего кода.

**Разведано заранее**:
- **bookmaker-ratings.ru** — WordPress, `sitemap_index.xml` открыт. Обзоры букмекеров
  лежат в `bookreviews-sitemap.xml` (511 адресов вида `/review/...`). WP REST API отвечает,
  но кастомный тип `bookreviews` в нём не опубликован (`rest_base` только `posts`/`pages`) —
  значит тексты идут не через WP API, а прямым запросом либо через firecrawl.
- **zarabota.com** — Blogger, а не WordPress. Карта сайта — индекс из страниц вида
  `sitemap.xml?page=1`, имён-паттернов (`post-sitemap`) там нет: фильтр по паттерну
  для этого источника должен отключаться, а не отсекать всё.

**Что делаем**:
- Миграция с двумя записями в `sources` (код, база, карта, паттерн, режим доступа).
- Поправка `sources/sitemap.js` под индекс без имён-паттернов (Blogger).
- Проверка кнопкой «Проверить источник» в панели.

**Критерии приёмки** (закрытие → tag `stage-4-done`):
- [ ] Проверка `bookmaker-ratings` кладёт в `articles` свежие `/review/...` с датами
- [ ] Проверка `zarabota` кладёт в `articles` свежие материалы с датами
- [ ] У материалов обоих источников заполнен `content` (текст, а не пустое поле)
- [ ] Старые шесть источников продолжают работать: проверка всех не даёт новых ошибок в журнале

## Этап 5 — Свои адаптеры под два источника

**Цель**: два сайта, которые не отдают карту сайта, всё равно поставляют темы.

**Разведано заранее**:
- **brokertribunal.com** — `sitemap.xml` существует, но `<urlset>` в нём **пустой**;
  `/brokers` отдаёт 404. Статьи вида `/brokers/<name>/overview` открываются напрямую (200).
  Нужен адаптер: найти рабочий листинг брокеров и снимать его.
- **sikayetvar.com** — площадка жалоб. На странице бренда (`/ru/pocket-option-ru`) лежит
  список жалоб `/ru/<бренд>/<слаг-жалобы>`. Ближайший аналог в коде — адаптер `scama`:
  «только тема», темой становится жалоба.

**Что делаем**:
- `src/sources/adapters/brokertribunal.js` и `src/sources/adapters/sikayetvar.js`,
  регистрация в `src/sources/discovery.js`.
- Миграция с двумя записями `sources` в режиме `custom`.
- Паузы между запросами: обход — залп по чужому хосту, на vklader это уже давало 403 по IP.

**Критерии приёмки** (закрытие → tag `stage-5-done`):
- [ ] Проверка `brokertribunal` даёт непустой список тем с датами
- [ ] Проверка `sikayetvar` даёт непустой список тем с датами
- [ ] Повторная проверка не создаёт дублей (дедуп по URL и по теме работает)
- [ ] Ни один адаптер не роняет прогон: сбой источника уходит в журнал ошибок

**Критерии приёмки** (закрытие → tag `stage-6-done`):
- [ ] Ручной прогон формирует план на все включённые группы без пересечения тем
- [ ] Посты уходят в ВК и Одноклассники по-настоящему (`publish_mode = live`)
- [ ] Крон отрабатывает сам, без ручного запуска
- [ ] За сутки журнал ошибок чист либо все записи разобраны
