# Дорожная карта — перенос под клиента Комарова

Это **не разработка с нуля**, а перенос готовой системы автопостинга (проект AlexNef,
`Downloads/ЗАКАЗЫ/posting_vk/vkposter`) под второго клиента. Код продукта уже написан и
проверен на проде: 14 этапов исходной разработки описаны в
[`07_ROADMAP_PRODUCT.md`](07_ROADMAP_PRODUCT.md) — этот файл читать как справочник
по устройству системы, чекбоксы там относятся к первому клиенту и здесь не действуют.

Что реально меняется при переносе:

1. **Другой сервер.** Первый клиент живёт на выделенном VPS со своим Postgres и своим
   Caddy. Этот проект подселяется на общий сервер okhost (`193.17.95.54`), где Postgres,
   Redis и Caddy — общие на всех клиентов. Значит: свой `postgres` из compose убрать,
   подключение брать из `.env.infra`, порты наружу не публиковать, задать `mem_limit`.
2. **Другие ключи и другой проект в postmypost** (`project_id 345029`), другие группы —
   9–10 в ВК плюс Одноклассники.
3. **Четыре новых источника** сверх шести имеющихся. Два берутся картой сайта, двум
   нужны свои адаптеры (карта пустая / структура нестандартная).
4. **Другой домен** — `vktop545.com`.

> **Где смотреть прогресс**: [`STATUS.md`](STATUS.md). Внутри каждого этапа ниже —
> чекбоксы acceptance-пунктов. Закрытие этапа сопровождается тегом `stage-N-done`.
>
> **Правило**: за один заход — один этап. Человек верифицирует его вживую, только после
> этого ставится тег и берётся следующий.

## Этап 1 — Адаптация под общий сервер okhost

**Цель**: проект соответствует правилам общего сервера — не поднимает свою БД, не
публикует порты, знает свой потолок памяти.

**Разведано**: `okhost new` кладёт в `.env.infra` не только `DATABASE_URL`, но и
`POSTGRES_HOST/PORT/DB/USER/PASSWORD` — ровно те переменные, которые приложение уже читает.
Значит **код подключения к БД трогать не нужно**, достаточно убрать из compose жёстко
прописанный `POSTGRES_HOST: postgres` и подключить `.env.infra` через `env_file`.

**Что делаем**:
- `docker-compose.yml` становится боевым файлом для okhost: без своего `postgres`,
  без `ports:`, `container_name: komarov-vkposter-app`, `mem_limit`, `cpus`,
  сети `data` и `edge` как external, `env_file: [.env.infra, .env]` (порядок важен —
  значения проекта перекрывают серверные).
- Dev-слой переезжает из `docker-compose.override.yml` в `docker-compose.dev.yml`:
  override подхватился бы автоматически и на сервере, увезя в прод свой Postgres,
  публикацию порта и монтирование кода. Локальный Postgres назван `infra-postgres`,
  как общий серверный, — топология одна и та же.
- Удаляем то, что относилось к схеме выделенного VPS: `docker-compose.prod.yml`,
  `deploy/Caddyfile`, `deploy/backup-db.sh` (бэкап делает `okhost backup`),
  `scripts/install.sh` (сервер уже подготовлен).
- `deploy/deploy.sh` переписан под один файл; проверка `/health` идёт изнутри
  контейнера — наружу порт не опубликован.
- `.github/workflows/deploy.yml`: каталог `/opt/projects/komarov-vkposter`,
  проверка по `https://vktop545.com`.

**Критерии приёмки** (закрытие → tag `stage-1-done`):
- [x] В `docker-compose.yml` нет сервисов `postgres`, `redis` и ни одного `ports:`
- [x] У сервиса `app` заданы `container_name: komarov-vkposter-app`, `mem_limit`, `cpus`
- [x] Подключение к БД приходит из `.env.infra`, в самом compose реквизитов нет
- [x] Локальный запуск двумя файлами по-прежнему работает: `/health` 200, вход в панель

## Этап 7 — Одна тема в ВК и в Одноклассниках

**Цель**: тема выходит дважды — один раз в какую-то группу ВК, один раз в какую-то группу
ОК. Задача клиента (17 августа): «логика чтобы в поиске был и ВК и ОК, но одной статьи».

**Сейчас не так**: планировщик держит правило «один материал — одна группа», и тема уходит
ровно в одно сообщество. Правило закреплено уникальными индексами
`run_items (run_id, article_id)` и `(run_id, post_id)`.

**Что делаем**:
- В `run_items` появляется сеть (`chanel_id` группы), уникальность становится
  «материал + сеть»: два слота на тему разрешены, но только в разных сетях.
- Раздача в `plan-run.js` идёт по сетям: кандидат кладётся в одну группу ВК и в одну
  группу ОК, внутри сети — по кругу, квоты групп соблюдаются как раньше.
- Слой публикации трогать не нужно: `publishPost` уже умеет отдавать один пост в несколько
  групп, на этом держалась заливка обложки один раз на пост.

**Следствие, о котором клиент предупреждён**: групп ОК всего три. При норме 5 постов
это 15 слотов в сутки против 45 в ВК, то есть продублировать удастся 15 тем, остальные
30 уйдут только в ВК. Больше — только если добавить сообщества ОК или поднять их норму.

**Критерии приёмки** (закрытие → tag `stage-7-done`):
- [x] План на сутки содержит темы, у которых ровно два слота: один ВК, один ОК
- [x] Ни одна тема не попадает дважды в одну сеть
- [x] Обложка заливается в postmypost один раз на пост, а не по разу на группу
- [x] Когда слоты ОК кончились, остальные темы уходят в ВК без сбоя плана

**Как проверено на проде** (17 августа, версия `dc6360f`):
- План на 12 групп (9 ВК + 3 ОК, по 5 постов): 58 слотов на 44 темы. Из них 14 тем
  получили по два слота — один ОК, один ВК; 30 ушли только в ВК. Дублей внутри сети — 0.
  Порядок слотов чередуется (ОК, ВК, ОК, ВК…), а не «сначала весь ВК».
- Обложка: пост #3 уже лежал черновиком в группе ВК с `file_id 52099893`.
  Отдача того же поста в группу ОК взяла тот же `file_id` без повторной заливки — в логе «Картинка поста #3 уже залита в postmypost, заливаем один раз»,
  публикация 31638798. Один пост, одна обложка, две сети.
- Слотов ОК меньше, чем тем: план не падает, остаток уходит в ВК (30 из 44 тем).

## Этап 9 — Вес обложек (в планах, без реализации)

**Цель**: раздел «Посты» открывается быстро. Замечание клиента от 17 августа: картинки
грузятся вечность, каждая по два мегабайта.

**Замерено на проде**: kie.ai отдаёт PNG, и это 1,5-1,9 МБ на обложку
(`post-1-…png` — 1 941 599 байт, `post-2-…png` — 1 534 897). Список постов и плитки в
прогонах вставляют этот же файл как есть, уменьшая его до 160 пикселей уже в браузере
(`<img src="${post.image_url}" style="width:160px">`). То есть страница на 60 постов тянет
около сотни мегабайт, чтобы показать полоску превью. Атрибута `loading="lazy"` тоже нет —
браузер грузит всё сразу, а не по мере прокрутки.

**Что делать** (порядок от самого дешёвого):
1. `loading="lazy"` и явные `width`/`height` на превью. Одна строка, снимает разовую
   загрузку всей страницы, вес файлов не меняет.
2. Превью отдельным файлом: при сохранении обложки писать рядом уменьшенную копию
   (ширина 320, JPEG качества 80 — это единицы килобайт) и подставлять её в списки.
   Полный файл остаётся для карточки поста и для postmypost.
3. Перевод самой обложки из PNG в JPEG. PNG для фотографической картинки с текстом —
   худший выбор: JPEG качества 85 даст те же 1920×1080 в 200-300 КБ. Проверить, умеет ли
   kie.ai отдавать сразу JPEG (тогда обработка не нужна вовсе), иначе конвертировать при
   сохранении. Учесть, что ВК и ОК всё равно пережимают картинку у себя.
4. Чистка старых файлов: сейчас в `media` лежат и промежуточные обложки одного поста
   (у поста #3 их три). Удалять предыдущую при перегенерации либо чистить по расписанию.

**Оговорка**: пункт 3 добавляет зависимость для обработки картинок (`sharp` или вызов
`ffmpeg`), пункты 1, 2 и 4 обходятся тем, что уже есть.

**Критерии приёмки** (закрытие → tag `stage-9-done`):
- [ ] Раздел «Посты» на 60 записей тянет меньше 5 МБ
- [ ] Обложка в карточке поста и в postmypost остаётся полноразмерной
