## Решения, зафиксированные на бутстрапе

- **Админка — один аккаунт** (админ = клиент), все разделы доступны. Обязательна завершённая
  логика доступа: вход → выход → смена пароля с инвалидацией сессий.
- **Промты хранятся в БД** и правятся в панели с версиями. Сид `post_prompt` — реальный промт
  клиента, копия в `docs/prompts/post_prompt.seed.txt`.
- **Redis не берём**: сервер 2 ядра / 2 ГБ, блокировки прогонов и очередь держим в Postgres
  (advisory locks + таблица задач).
- **Картинки храним у себя** (`/media` volume, отдаём по https домена). Временный URL от kie.ai
  в postmypost не отдаём — истекает до отложенной публикации.
- **Git**: свой репозиторий внутри `vkposter`, ветка `dev`. Папка вложена в чужой репо —
  в родительский корень не коммитим. **Remote (GitHub) создаётся на этапе 12** вместе с
  автодеплоем — до этого коммиты только локальные, `git push` не делаем.

**2026-07-28 — Этап 11: Панель наблюдаемости — tag `stage-11-done`**
Три раздела: «Прогоны» (+ карточка `/runs/:id`), «Опубликовано» и «Ошибки». Ошибки живут
в новой таблице `app_errors`.

Три решения, которые стоит помнить:
1. **Журнал сбоев — отдельная таблица, а не выборка из `run_items`/`publications`.** Там лежит
   только текст сообщения, а критерий требует шаг конвейера, внешний сервис и **тело ответа**.
   Плюс сбои бывают вне прогона: проверка источника, тик планировщика, пустой план.
2. **Запись делает один `captureError`,** который разматывает цепочку `cause` до `HttpError` —
   оттуда сервис, статус, адрес и тело. Ради этого `PmpError`/`KieError`/`OpenRouterError`
   теперь сохраняют `cause`: без него в журнал не попадал ни адрес запроса, ни тело ответа.
3. **Один сбой — одна запись.** Тот, кто поймал ошибку ближе к месту, ставит на ней
   `captured`, и слот прогона второй, более бедной записи не делает. Первый же прогон
   показал дубли: сбой публикации писался и из `publishPost`, и из слота.

Проверено на заглушках: прогон #77 — 8 слотов, здоровая группа получила 3 поста, у сломанной
(аккаунт, которого нет в postmypost) 5 слотов упали, прогон завершился `done` — ошибка внешнего
API прогон не обрывает. Публикация на заглушке `pubfail` дала в журнале стадию «публикация»,
сервис `postmypost`, `HTTP 422`, адрес запроса и тело `[{"message":"Заглушка: публикация

**2026-07-28 — Этап 10: Разовое наполнение из архива — tag `stage-10-done`**
Раздел «Из архива»: источники, период (с/по), лимит постов и объём в день на группу.
Задание собирает материалы за период, отбрасывает те, по которым пост уже был, и раскладывает
очередь от свежих к старым по дням.

Четыре решения, которые стоит помнить:
1. **Задание — строка в БД (`archive_jobs`), а не объект в памяти.** «Остановить» ставит статус
   `stopping`, исполнитель читает его перед каждым слотом: остановка работает после рестарта
   контейнера и из другого процесса, прогресс виден в панели без обращения к процессу-владельцу.
2. **План лежит в `run_items` (`kind = 'archive'`)** — как у обычного прогона. Даром достаются
   продолжение после перезапуска, защита от повторной публикации и то, что cron-прогон не берёт
   занятые материалы. Из `unfinishedCycle`/`lastCycle` вид `archive` исключён: чужой план
   обычный прогон разложил бы по своим правилам, а разовая заливка не должна двигать расписание.
3. **Растягивание по дням — через `post_at`.** Публикации создаются сразу, но встают в postmypost
   на будущие даты. Ради этого дневной лимит группы теперь считается **на день слота**
   (`groups.publishedOn`), а не на день создания записи: иначе задание упиралось бы в лимит
   первого дня, хотя на стене выходит ровно норма.
4. **У обнаружения появилась верхняя граница периода** (`until`; у WP API ещё и постраничный
   обход). Без неё активный сайт на запрос «за 2025 год» отдавал бы свои свежие материалы —
   ровно та грабля, что была записана на этапе 9 про добор.

Проверено на заглушках, группы-заглушки 900001/900002: задание #1 (2025-01-01..2025-06-30,
лимит 8) дало очередь из 8 слотов на 2 дня, даты материалов монотонно 30.06 → 26.06.2025;
задание #2 на том же периоде не пересеклось с #1 ни одним материалом и ни одной темой;
остановка #2 на 30 слотах — опубликовано 3, погашено 27, публикаций по погашенным нет;
задание #4 остановлено во время публикации — пост #69 остался в базе (`ready`, с обложкой),

**2026-07-27 — Этап 9: Автономный cron + ручной режим — tag `stage-9-done`**

Оставлен в базе как образец, не опубликован.

Два дефекта, найденных проверкой:
1. **Осознанный повтор темы падал сырой ошибкой Postgres.** `articles_topic_active_uidx`
   не пускает второй активный материал с той же темой — и правильно, иначе автоматический
   дедуп перестал бы быть гарантией. Ручной повтор получает свой ключ `<тема>-m2` при
   человеческом `topic_name`; `refreshTopic` для него не вызывается, иначе он пересчитал бы
   ключ по заголовку, нашёл занятую тему и пометил материал дублем — то есть отменил бы
   ровно то, на что человек поставил галочку.

Грабля на UAT: вход внезапно начал отдавать 401 на верный пароль. Причина — `.env` в CRLF,
хеш был посчитан от значения с хвостовым `\r`, а последующая перезапись файла в LF значения
рассинхронизировала. Починено `trim` в `src/config.js` — важно не только для пароля: ключ API
с `\r` давал бы загадочный 401 от провайдера.

Поднято: `app` (Node 22 ESM) + `postgres:16`, оба healthy. `/health` отдал

сбросом uptime 22 → 10 сек при правке `src/` (в логе `restarting due to changes`).

Две грабли, решённые по ходу:
1. `node --watch` не видит правки через bind-mount Docker Desktop на Windows (inotify не
   пробрасывается) → перешли на `nodemon --legacy-watch` (polling).
2. `TZ=Europe/Moscow` на alpine игнорируется без пакета `tzdata`, контейнер жил в UTC. Критично
   для проекта: `post_at` в postmypost требует `+03:00`, расписание задаётся в часах. Поставили
   `tzdata`, `date` в обоих контейнерах отдаёт MSK.

обвязка для firecrawl/openrouter/kie.ai/postmypost; контрольные суммы в раннере миграций;
`request-id` через AsyncLocalStorage.

## Протокол обновления

**При старте сессии**:
1. Прочитать этот файл.
2. `git tag -l "stage-*"` и сверить с колонкой «Закрывающий тег». Тег без записи в таблице = таблица устарела, обновить.
3. `git log --oneline -10` — что менялось последним.
4. Только после этого приступать к работе.

**При взятии этапа в работу**:
1. Обновить «Текущий этап» и «Активная работа».
2. Статус 🚧 в таблице.
3. Закоммитить отдельно: `chore(status): start stage N`.

**При закрытии этапа**:
1. Убедиться, что все чекбоксы в `07_ROADMAP.md` отмечены `[x]` и реально проверены человеком.
2. Создать тег: `git tag stage-N-done -m "<описание>"`.
3. В таблице: ✅, «Закрывающий тег», «Последний коммит» (`git rev-parse --short HEAD`), «Дата закрытия».
4. Добавить запись в «Историю закрытий».
5. Указать новый «Текущий этап» и «Следующий шаг».
6. Закоммитить: `chore(status): close stage N`.

**Если этап заблокирован**:
1. Статус ⏸ в таблице.
2. В «Известные блокеры»: что блокирует, кого ждём, что нужно для разблокировки.
