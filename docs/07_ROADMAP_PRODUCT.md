# Дорожная карта реализации — Автопостинг ВК (обзоры-отзывы)

13 этапов от пустого репозитория до прод-готовности. Каждый этап заканчивается
**демонстрируемым результатом** (что можно потрогать руками).

Ключевая идея: **MVP-first**. Этапы 0–6 выстраивают тонкую, но живую вертикаль
«источник → текст → картинка → пост в ВК». Этапы 7–12 наращивают объём,
автономность и прод.

> **Где смотреть прогресс**: текущий статус всех этапов — в [`STATUS.md`](STATUS.md).
> Внутри каждого этапа ниже — чекбоксы конкретных acceptance-пунктов. Закрытие этапа
> сопровождается git-тегом `stage-N-done`.
>
> **Правило**: за один заход выполняется **один** этап. Человек верифицирует его вживую,
> только после этого ставится тег и берётся следующий.

| # | Этап | Главный артефакт | Зависит от |
|---|---|---|---|
| 0 | Каркас в Docker | `docker compose up` → `/health` отвечает, миграции применены, логи на русском | — |
| 1 | Схема БД + вход в панель | Логин по паролю, выход, смена пароля; таблицы и 6 источников в БД | 0 |
| 2 | Обнаружение и извлечение статей | Кнопка «Проверить источники» → в БД свежие URL с датами и текстом | 1 |
| 3 | Дедуп по URL и по теме | Повторный прогон не создаёт дублей; одна тема с двух сайтов схлопывается | 2 |
| 4 | Генерация текста поста (OpenRouter) | Из статьи получается готовый пост 1200–2200 симв. с рекламным блоком | 3 |
| 5 | Генерация картинки (kie.ai) | Обложка доступна по публичному URL нашего домена | 4 |
| 6 | Публикация в ВК (postmypost) | Реальный пост с картинкой на стене тестовой группы | 5 |
| 7 | Группы ВК в панели | Клиент включает группу из списка postmypost, задаёт постов/день | 6 |
| 8 | Уникальность по группам + расписание | Прогон на 2 группы: у каждой свой набор постов, время разнесено | 7 |
| 9 | Автономный cron + ручной режим | Прогон стартует сам по расписанию; из панели можно сделать пост по ссылке/теме | 8 |
| 10 | Разовое наполнение из архива | Указал период → очередь постов от свежих к старым | 9 |

## Этап 0 — Каркас в Docker

**Цель**: пустой, но рабочий проект, в котором есть всё для следующих этапов — включая
полный слой логов, который дальше обрастает событиями, а не переписывается.

**Что делаем**:
- `docker-compose.yml`: сервис `app` (Node.js 22, ESM) + `postgres:16`. Redis не берём —
  сервер 2 ядра / 2 ГБ, очередь и дебаунс держим в Postgres (advisory locks + таблица задач).
- Автосборка при изменениях: в dev — bind-mount + `nodemon --legacy-watch` (polling; нативный
  `node --watch` правки через bind-mount Docker Desktop на Windows не видит); в прод — пересборка образа.
- Автомиграции: свой раннер на SQL-файлах, запускается на старте контейнера **до** поднятия
  HTTP-сервера, идемпотентно (журнал + контрольные суммы + advisory lock).
- Express + `/health` (проверяет коннект к БД и версию применённых миграций).
- Логирование `pino` + `pino-pretty`, вывод на русском. Ядро слоя логов:
  `request-id` (генерируется на входе, протаскивается через весь путь через AsyncLocalStorage),
  логгер-обёртка для HTTP-запросов (метод, URL, статус, латентность, тело при ошибке),
  для вызовов ИИ (модель, латентность, токены), для внешних API (имя + аргументы + результат).
- `.env.example` со всеми ключами; реальный `.env` в `.gitignore`.
- `git init` внутри `vkposter`, ветка `dev` (папка вложена в чужой репо — в родительский корень не коммитим).

**Критерии приёмки** (закрытие → tag `stage-0-done`):
- [x] `docker compose up` поднимает `app` и `postgres`, оба healthy
- [x] `GET /health` отдаёт 200 с версией применённых миграций и `db: ok`
- [x] Правка файла в `src/` перезапускает приложение без ручного рестарта контейнера
- [x] Повторный `docker compose up` не ломает БД: миграции применяются идемпотентно
- [x] В логах видно русские сообщения с датой/временем и `request-id` на каждый HTTP-запрос
- [x] Искусственная ошибка внешнего запроса пишет в лог статус, тело ответа и `request-id`
- [x] `git log` в `vkposter` содержит только коммиты этого проекта, ветка `dev`

## Этап 1 — Схема БД + вход в панель

**Цель**: есть закрытая паролем панель с завершённой логикой доступа, и есть схема,
в которую дальше пишутся данные.

**Что делаем**:
- Миграции таблиц:
  - `sources` — источник, тип sitemap, откуда брать свежее, режим (`text` / `topic_only`), активен
  - `articles` — найденные материалы: url, source_id, lastmod, нормализованная тема, текст, статус
  - `posts` — сгенерированные посты: title, body, image_url, article_id
  - `publications` — факт публикации: post_id, group_id, postmypost id, статус, время
  - `groups` — группы ВК: postmypost account_id, name, постов/день, активна
  - `settings` — key/value: окно свежести, расписание, промты, лимиты
  - `runs` — прогоны: старт, финиш, итог, ошибки
  - `users` — логин, хеш пароля (argon2/bcrypt), дата смены пароля
- Сид: 6 источников из брифа (vklader, offbez, kaper.pro, cryptorussia, all-comment, scama.net)
  с зафиксированным для каждого способом обнаружения.
- Вход: один аккаунт (админ = клиент), сессия в cookie (httpOnly, signed), логин/пароль из `.env`
  при первом старте, дальше — хеш в БД.
- Полная логика доступа: **вход → выход → смена пароля**, при смене пароля старые сессии
  инвалидируются. Все страницы кроме `/login` закрыты.
- Каркас UI: боковое меню с разделами (пока пустыми) — Группы, Источники, Настройки,
  Промты, Прогоны, Опубликовано, Ручной режим.

**Критерии приёмки** (закрытие → tag `stage-1-done`):
- [x] Открытие любой страницы без входа редиректит на `/login`
- [x] Вход по паролю пускает в панель, в логе видно «вход выполнен» с IP и `request-id`
- [x] Кнопка «Выход» завершает сессию, повторное открытие панели снова просит пароль
- [x] Смена пароля работает: новый пароль пускает, старый — нет
- [x] После смены пароля ранее открытая сессия в другом браузере разлогинена
- [x] В `sources` 6 записей с корректным типом sitemap и режимом; проверяется SQL-запросом
- [x] Все таблицы созданы миграциями: `\dt` показывает 8 прикладных + 2 служебных
      (`schema_migrations`, `app_meta` с этапа 0)
- [x] Неверный пароль пишет в лог попытку входа и не пускает

## Этап 2 — Обнаружение и извлечение статей

**Цель**: система сама находит свежие материалы на источниках и вытаскивает их текст.

**Что делаем**:
- Дискавери через sitemap (основной способ, не краулинг): читаем sitemap-индекс, берём
  дочерние карты по списку допустимых типов источника, **нужную выбираем по `lastmod`
  из индекса, а не по имени файла**. На пресейле считалось, что у cryptorussia свежее
  лежит только в `services-sitemap`, а по факту оно есть в обоих пулах и распределение
  меняется — сортировка по `lastmod` к таким переменам устойчива.
- Индивидуальные адаптеры под нестандартные: `all-comment.com` (карта сайта пустая →
  обнаружение через WP REST API, режим «только тема»), `scama.net/check` (403 напрямую →
  только через firecrawl; темы берутся из таблицы заявок: домен + дата + вердикт).
- Извлечение текста: **WP REST API как основной путь** (у всех пяти WP-источников открыт
  и отдаёт полный текст бесплатно), firecrawl — страховка и единственный путь к scama.net.
  Экономия лимита (1000/мес): не тянем то, что уже в `articles`, не тянем при `topic_only`.
- Реальная дата публикации берётся из WP API (`date_gmt`) и хранится отдельно от `lastmod`:
  массовое пересохранение записей на сайте поднимает `lastmod` у сотен архивных статей,
  и сортировка «от свежих к старым» по нему врала бы.
- Фильтр свежести по настраиваемому окну (дата отсечки из `settings`).
- Раздел «Источники» в панели: список, вкл/выкл, «Проверить» по одному и по всем,
  сводка по материалам, список последних найденных.
- Ретраи с бэкоффом на таймауты и 5xx; блокировка на источник, чтобы параллельные
  проверки одного сайта не пересекались; каждый запрос в логе.

**Критерии приёмки** (закрытие → tag `stage-2-done`):
- [x] Кнопка «Проверить» по vklader добавляет в `articles` свежие URL с датами
- [x] Для cryptorussia проверяются оба пула карт (`post-sitemap` и `services-sitemap`),
      нужные выбираются по `lastmod` из индекса; свежие материалы попадают в БД
- [x] Текст статьи cryptorussia достаётся из кастомного типа записей `services` через
      WP API, а не через firecrawl
- [x] `scama.net/check` отдаёт темы (через firecrawl), несмотря на 403 при прямом запросе
- [x] `all-comment.com` даёт темы в режиме `topic_only`, текст не тянется
- [x] Изменение окна свежести в настройках меняет число найденных материалов
- [x] Повторная проверка того же источника не расходует firecrawl на уже извлечённые статьи
- [x] В логе на каждый внешний запрос видно URL, статус, латентность; при ошибке — тело ответа
- [x] Искусственный таймаут firecrawl приводит к ретраю, а не к падению прогона

## Этап 3 — Дедуп по URL и по теме

**Цель**: один проект не уходит в группы дважды, даже если ссылки разные.

**Что делаем**:
- Дедуп по URL: нормализация (схема, `www`, слеш, utm) + уникальный индекс.
- Дедуп по теме: извлечение названия проекта из заголовка/URL, нормализация
  (регистр, латиница/кириллица, `.com`/`.io`, пробелы, дефисы), хранение `topic_key`
  с уникальным индексом.
- Тема считается из трёх источников по убыванию надёжности: подсказка адаптера →
  заголовок → slug адреса. Заголовка при обнаружении через sitemap нет, он появляется
  только после извлечения текста — поэтому тема считается дважды, второй раз уточняется.
  Варианты, полученные разными путями, хранятся вместе (`topic_aliases`) и участвуют
  в сверке все: иначе «Atlas capital» с одного сайта не сойдётся с «atlas-capital-otzyvy»
  с другого.
- Транслитерационные варианты сворачиваются (c→k, w→v, y/j→i): «Atlas capital» и
  «Атлас Капитал» — один проект.
- Отсев не-материалов: страницы-листинги разделов (`cryptorussia.ru/services`) и адреса,
  по которым тему определить нельзя.
- Учёт «уже публиковали»: материал с известным `topic_key` не попадает в очередь.
- В панели у материала видно, почему он отклонён (дубль URL / дубль темы), плюс кнопка
  пересчёта тем после правки правил нормализации.

**Критерии приёмки** (закрытие → tag `stage-3-done`):
- [x] Повторный прогон по всем источникам не добавляет ни одной новой записи в `articles`
- [x] Две статьи про один проект с разных сайтов дают один `topic_key`, вторая помечена дублем
- [x] URL с `utm`-метками и без них считаются одним материалом
- [x] В панели у отклонённого материала показана причина отклонения
- [x] Попытка вставить дубль напрямую в БД падает на уникальном индексе (защита на уровне схемы)
- [x] Служебные страницы-листинги в выборку материалов не попадают

## Этап 4 — Генерация текста поста (OpenRouter)

**Цель**: из материала получается готовый к публикации текст по промту клиента.

**Что делаем**:
- Клиент OpenRouter: основная модель `google/gemini-2.5-flash-lite`, фолбэк в массиве
  `models` (`deepseek/deepseek-v4-flash:nitro`), строгий JSON на выходе
  (`{"title": "...", "body": "..."}`) через structured outputs.
- Промты **из БД**, раздел «Промты» в панели: `post_prompt`, `image_prompt`, с версиями
  и возможностью откатиться. Сид `post_prompt` — реальный промт клиента
  (`docs/prompts/post_prompt.seed.txt`), правится в панели без деплоя.
- Режим «текста нет» — ИИ пишет статью по теме сам (для `all-comment`, `scama.net`).
- Постобработка регулярками: убрать markdown, лишние пробелы, и тире «—» **внутри
  предложений**. Осторожно: в клиентском промте «—» используется как маркер булитов
  в начале строки — эти не трогаем. Эмодзи-иконки (🔰 ❗️ ✅) — осознанный стиль клиента
  для ВК, сохраняем.
- Валидация: длина 1200–2200 символов, слово «отзыв» + название проекта в первом абзаце,
  рекламный блок со ссылкой `https://proverka-zarabotka.online` на месте. Не прошло → ретрай.
- Ретраи и бэкофф на таймауты/429/5xx, `Retry-After`; логирование модели, латентности, токенов.

**Критерии приёмки** (закрытие → tag `stage-4-done`):
- [x] Из материала vklader получается пост: заголовок + тело 1200–2200 символов
- [x] Первый абзац начинается с одного из зачинов промта, есть слово «отзыв» и название проекта
- [x] Есть два подзаголовка с булитами и блок «Итог» на 2–4 предложения
      *(проверяется валидацией: минимум 4 булита и строка «Итог», иначе повтор генерации)*
- [x] В конце текста присутствует рекламный блок со ссылкой на `proverka-zarabotka.online`
      *(проверяется валидацией; ссылка берётся из рекламного блока активного промта, настройка `ad_link` — запасная)*
- [x] В тексте нет markdown-разметки и тире «—» внутри предложений; булиты «— пункт» и
      эмодзи-иконки (🔰 ❗️ ✅) сохранены
- [x] Материал в режиме `topic_only` (только тема, без текста) тоже даёт валидный пост
- [x] Правка промта в панели меняет результат следующей генерации без перезапуска
- [x] Откат промта к предыдущей версии работает
- [x] Принудительная ошибка основной модели переключает на фолбэк, пост всё равно создаётся

## Этап 5 — Генерация картинки (kie.ai)

**Цель**: у каждого поста есть обложка, доступная по стабильному публичному URL.

**Что делаем**:
- Клиент kie.ai `gpt-image-2` text-to-image: создание задачи → поллинг статуса.
- Промт обложки из БД (`image_prompt`): стиль YouTube-обложки, русский текст,
  2–4 крупных слова, читаемость при 160 px.
- **Своё хранилище**: скачали результат → положили в `/media` (volume) → отдаём по
  `https://probizn.website/media/...`. Временный URL от kie.ai в postmypost не отдаём —
  он истекает до отложенной публикации.
- Проверка остатка кредитов перед пачкой (`/chat/credit`), чтобы не упасть на 402 посередине.
- Ретраи на нестабильность провайдера (таймауты, 5xx), фолбэк-поведение при исчерпании.

**Критерии приёмки** (закрытие → tag `stage-5-done`):

      *(в dev — `PUBLIC_BASE_URL`, то есть `http://localhost:3000/media/...`; домен

- [x] В логе видно id задачи kie.ai, латентность и итоговый локальный путь

## Этап 6 — Публикация в ВК (postmypost)

**Цель**: полная вертикаль замкнута — материал доезжает до стены группы ВК.

**Что делаем**:
- Клиент postmypost v4.1: `POST /upload/init` → поллинг `GET /upload/status` (до `file_id`,
  таймаут 120 с) → `POST /publications`.
- Переиспользование `file_id`: одна картинка заливается один раз и вставляется в несколько групп.
- Проверка `connection_status` аккаунта перед постингом.
- Сначала `publication_status: 4` (черновик) для UAT, затем переключатель «реальная публикация»
  (`5`) в настройках.
- Время `post_at` в МСК (`+03:00`).
- Обработка 429 по `Retry-After`, ретраи на 5xx, ответ всегда как массив — берём `[0]`.
- Запись факта в `publications`, отметка `topic_key` как опубликованного.

**Критерии приёмки** (закрытие → tag `stage-6-done`):

## Этап 8 — Уникальность по группам + расписание

**Цель**: в каждую группу уходит **свой** набор постов без пересечений, распределённый по времени.

**Что делаем**:
- Распределение материалов по группам: один материал → одна группа (никаких пересечений),
  учёт `posts_per_day` каждой группы.
- Сортировка при постинге **от свежих к старым**.
- Расписание: интервал запуска (каждые N часов / раз в день / cron-выражение) в настройках.
- Распределение постов внутри окна по времени (антиспам): равномерные слоты с джиттером.
- Дебаунс/склейка: параллельные прогоны не наступают друг на друга (advisory lock),
  прерывание прогона логируется и не оставляет полу-опубликованных постов.

**Критерии приёмки** (закрытие → tag `stage-8-done`):
- [x] Прогон на 2 группы по 3 поста даёт 6 разных материалов, пересечений нет (проверяется SQL)
      — SQL по `run_items`: 6 слотов, 6 разных `article_id`, по 3 на группу; сверх этого
      пересечение запрещено уникальными индексами `(run_id, article_id)` / `(run_id, post_id)`
- [x] Внутри группы посты идут от свежих к старым по дате материала
      — кандидаты сортируются по `COALESCE(articles.published_at, lastmod) DESC` до раздачи по кругу
- [x] Время публикаций разнесено по слотам, а не свалено в одну минуту
      — равномерные слоты внутри окна + джиттер, минуты не повторяются (postmypost округляет до минуты)
- [x] Смена расписания на «каждые 5 часов» отражается в времени следующего запуска в панели
      — и в «Следующем запуске», и в самих слотах: в режиме интервала план не выходит за
      следующий запуск (10:01-14:10 против 10:01-19:13 в режиме «раз в день»)
- [x] Запуск второго прогона во время первого не создаёт дублей — второй ждёт или отклоняется

- [x] Прерванный прогон при следующем запуске продолжается корректно, без повторной публикации

**Проверено на заглушке `/_debug/pmp`.** Живой прогон с настоящими черновиками в postmypost

## Этап 13 — Сбор материала поиском (firecrawl)

**Цель**: пост про тему без готовой статьи пишется по найденным в сети фактам, а не

## Этап 14 — Чистый журнал ошибок

**Цель**: в разделе «Ошибки» не копятся повторяющиеся сбои. Всё, что остаётся, —
это либо внешние деньги (кредиты firecrawl и kie.ai), либо действительно новое.

**Зачем**: клиент смотрит журнал каждый день и видит там одно и то же. Разбор записей
за неделю дал четыре причины, ни одна из которых не является настоящей поломкой:

- **каждая ошибка записана дважды.** `generatePost` пишет запись и бросает новую ошибку
  без пометки `captured`, поэтому слот прогона пишет вторую. Половина журнала — дубли;
- **проверка «в первом абзаце нет названия проекта» не переживает склонение.** Тема
  «Ксения Зюзгина», в тексте «Ксении Зюзгиной» — точного вхождения нет, и нормальный
  пост браковался три раза подряд;
- **мусорное название темы делает проверку невыполнимой.** У материала 51 тема
  извлеклась как «https» — в первом абзаце такого не будет никогда;
- **отказ модели по фильтру контента** (`Gemini blocked the request: PROHIBITED_CONTENT`)
  не переключает на резервную модель: это 400 на запросе, а не отказ провайдера, и
  список `models` в OpenRouter здесь не срабатывает.

**Что делаем**:
- пометка `captured` на ошибке генерации: одна беда — одна запись в журнале;
- сравнение названия проекта по основе слова, чтобы склонения и падежи не ломали проверку;
- служебные слова (`http`, `https`, `www`) выбрасываются из названия темы: если значимых
  слов не осталось, проверка не применяется;
- спасение поста, забракованного ТОЛЬКО отсутствием названия, — отдельным вызовом модели
  «впиши название в первый абзац, остальное не трогай» (по образцу сокращения по длине);
- забытый рекламный блок дописывается кодом: он неизменный и дословный, берётся
  из активного промта, чтобы правка промта клиентом не разъезжалась с кодом;
- отказ по фильтру контента переводится в повтор на резервной модели.

**Критерии приёмки** (закрытие → tag `stage-14-done`):
- [x] Одна ошибка даёт ровно одну запись в журнале (проверено 04.08 на живом отказе
      модели: запись #114 одна, до фикса такие шли парами)
- [x] Пост по теме-имени человека («Ксения Зюзгина») проходит проверку названия
      (материал 508, пост #323 с первой попытки; раньше три попытки и брак)
- [x] Тема, у которой название состоит из мусора, постов не бракует (проверено на
      реальных темах: «https playfortunage8d959 com ru login», clw, Merabo.ru)
- [ ] Пост, забракованный только отсутствием названия, дописывается и публикуется,
      а не уходит в брак
- [ ] Забытый моделью рекламный блок дописывается кодом из промта, а не бракует пост
- [x] Отказ модели по фильтру контента даёт пост с резервной модели, а не сбой слота
      (материал 651: Gemini отказал, deepseek написал, пост #325)
- [ ] За сутки после выката в журнале нет ни одной записи, кроме внешних лимитов
      (firecrawl, kie.ai)
