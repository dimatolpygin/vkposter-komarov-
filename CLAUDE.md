## Стек и решения

- Node.js 22 (ESM) + Express, Postgres 16, Docker Compose. Redis не используем.
- Планировщик — `node-cron` внутри приложения. Блокировки прогонов — Postgres advisory locks.
- Логи — `pino` + `pino-pretty`, **на русском**, со сквозным `request-id` (AsyncLocalStorage).
  Логировать каждый tool-call, каждый вызов ИИ (модель/латентность/токены), каждый внешний
  запрос (метод/статус/тело при ошибке), склейку/дебаунс, прерывания, ошибки с контекстом.
- Автомиграции применяются на старте контейнера до подъёма HTTP-сервера, идемпотентно.
- Внешние API нестабильны (kie.ai, openrouter, firecrawl) — везде ретраи с бэкоффом,
  учёт `Retry-After`, фолбэк-модель у openrouter.
- Промты — в БД, правятся в панели, с версиями.
- Эмодзи-иконки в текстах постов — **осознанный стиль клиента**, глобальное правило
  «без эмодзи» на клиентский промт не распространяется. На UI-тексты панели — распространяется.

## Грабли окружения (проверено на этапах 0-2, не переоткрывать)

- **Автосборка в dev — только `nodemon --legacy-watch`** (polling). Нативный `node --watch`
  правки хостовых файлов через bind-mount Docker Desktop на Windows не видит: inotify
  не пробрасывается.
- **`tzdata` в образе обязательна.** Без пакета переменная `TZ` на alpine игнорируется
  и контейнер живёт в UTC. Проекту нужна МСК: `post_at` в postmypost идёт с `+03:00`,
  расписание задаётся в часах.
- **Значения окружения читаются через `trim`** (`src/config.js`). `.env`, отредактированный
  на Windows, приходит с CRLF, и значение получает хвостовой `\r`: пароль перестаёт
  совпадать, а API-ключ даёт загадочный 401 от провайдера.
- **Новую переменную окружения надо добавить и в `docker-compose.yml`** — там переменные
  перечислены явно, наличия в `.env` недостаточно.
- Правка уже применённой миграции падает по контрольной сумме — это защита, а не баг.
  Нужна новая миграция.

## Факты об источниках (разведаны на этапе 2)

- **У всех пяти WP-источников открыт `/wp-json/wp/v2/posts` и отдаёт полный текст статьи.**
  Извлечение идёт через него, `firecrawl` — только страховка. Лимит firecrawl (1000/мес)
  расходуется почти исключительно на scama.net.
- **Какая дочерняя карта sitemap несёт свежее — определяется по `lastmod` из индекса, а не
  по номеру в имени файла.** У vklader свежее в последнем номере, у cryptorussia — в первом.
- **Если `lastmod` у всех карт одинаковый, сортировка по нему бесполезна.** У vklader
  генератор карт штампует всем пятнадцати файлам одно время, порядок остаётся как в
  индексе, а там первым идёт архив 2015 года. Обход набирал 50 старых адресов из первой
  карты и до свежих не доходил: источник был активен, а в очередь не попадал ни разу
  (0 публикаций против 47 у all-comment). Лечение в `sources/sitemap.js`: при одинаковых
  `lastmod` карты читаются **с конца** и обход останавливается на двух пустых подряд.
- **Обход сайта — это залп по чужому хосту.** Пятнадцать запросов карт плюс тридцать за
  текстами дали 403 по IP сервера на vklader (WP API тоже закрылся, снялось само за ~час).
  Отсюда паузы: 800 мс между картами, 600 мс между статьями.
- **cryptorussia: свежее лежит в кастомном типе записей `services`**, не в `post`. Отсюда
  поле `sources.wp_post_types`. Бриф утверждал, что `post-sitemap` — архив 2024, а свежее
  только в `services-sitemap`; сейчас свежее в обоих пулах.
- **`articles.published_at` (реальная дата из WP API) приоритетнее `lastmod`** при сортировке
  «от свежих к старым»: массовое пересохранение записей подняло `lastmod` у 729 архивных
  статей cryptorussia внутри окна свежести.
- **all-comment.com**: `/sitemap.xml` редиректит на пустой `/blog/sitemap.xml/`. Обнаружение —
  через WP REST API. Текста в статьях мало, режим «только тема».
- **scama.net**: 403 на любой прямой запрос, через firecrawl открывается. Статей нет —
  на `/check` таблица заявок (домен + дата + вердикт), она и даёт темы.
- В выборку могут попадать служебные страницы-листинги (например `cryptorussia.ru/services`) —
  их отсекает дедуп по теме.

## Длина поста (проверено на живых прогонах)

`google/gemini-2.5-flash-lite` лимит длины из промта не держит: по Honee AI подряд
вышли 2918, 2035 и 3426 символов при потолке 2200. Констатация «длинно: 3426, нужно
до 2200» не работает — символы модель не считает. Работает связка из трёх мер
(`services/generate-post.js`):

1. Требование по длине дублируется **в конце пользовательского сообщения**, рядом с
   задачей, а не только в хвосте системного промта. После этого попытки пошли
   3000 → 2487 → 2264 вместо 2918 → 3426.
2. `shrinkBody` просит убрать **долю** («примерно на 25 процентов»), а не уложиться в
   число, и вызывается до трёх раз подряд от новой длины.
3. `trimBulletLists` (`lib/text-clean.js`) кодом убирает пункты сверх трёх в блоке:
   промт просит по три, модель раздаёт по пять-шесть. Рекламный блок и «Итог» не трогает.

Спасение включается, только если единственная претензия — длина: всё остальное в посте
уже верно, и терять тему из-за лишних символов незачем.

## Заглушка провайдера ИИ (этап 4)

Позволяет гонять конвейер генерации без расхода кредитов и без зависимости от провайдера.
В dev подставить в `.env`:

```env
OPENROUTER_BASE_URL=http://127.0.0.1:3000/_debug/openrouter
```

Режим задаётся **сегментом пути** (query-строка не доживает: клиент дописывает
`/chat/completions` к baseUrl):

| Путь | Что проверяет |
|---|---|
| `/_debug/openrouter` | нормальная генерация |
| `/_debug/openrouter/dirty` | постобработку: markdown и тире внутри предложений |
| `/_debug/openrouter/fail2` | ретраи с бэкоффом на 503 |
| `/_debug/openrouter/invalid1` | повтор при непрошедшей валидации |

Флаги сочетаются через дефис: `fail1-invalid1-dirty`. Строка `[[маркер:ТЕКСТ]]` в промте
попадает в заголовок поста — так проверяется, что до модели дошёл промт из БД.
Перед сдачей вернуть `OPENROUTER_BASE_URL=https://openrouter.ai/api/v1`.

Грабли, найденные на этапе 4:
- **Ключ OpenRouter в `dostupi.txt` записан с двумя лишними символами на конце.** После
  `sk-or-v1-` должно быть ровно 64 hex-символа, там 66 — и провайдер отвечает `401 User not
  found`, то есть как на случайную строку, а не «нет денег». Верное значение оканчивается
  на `bc93109`. Прежде чем подозревать баланс, считайте длину ключа.
- **Неверный идентификатор модели фолбэк не включает**: это `400` на валидации запроса, до
  маршрутизации по провайдерам. Фолбэк из массива `models` срабатывает на отказ провайдера
  (проверено моделью, недоступной аккаунту — ответила вторая в массиве).
- **«Первый абзац» — это первые два блока текста, а не первый.** Заголовок приходит отдельным
  полем схемы, но модель часто дублирует его первой строкой тела, и зачин со словом «отзыв»
  оказывается во втором блоке. Проверка по одному блоку браковала нормальные посты.
- **`\b` в регулярках не работает с кириллицей** (в JS граница слова только ASCII):
  `/^\s*итог\b/i` не находит строку «Итог:». Проверять без `\b`.
- **Длинных тире «—» в готовом тексте не остаётся вообще** (требование заказчика).
  Внутри предложения тире убирается, а там, где оно осмысленно (булиты, рекламный блок),
  заменяется коротким дефисом. Проверка: `SELECT count(*) FROM posts WHERE body LIKE '%—%'`
  должна давать 0. Для уже сохранённых постов есть разовый прогон
  `docker compose exec app node scripts/reclean-posts.mjs` — перегенерировать текст
  через модель ради смены правил чистки не нужно.
- **Ссылка из markdown дублировалась**: модель пишет `[https://site.ru](https://site.ru/)`,
  текст и адрес различаются только слэшем, и строгое сравнение оставляло «ссылка (ссылка)».
  Сравнение идёт без хвостового слэша.
- **Ссылка рекламного блока живёт в промте, а не в настройке.** Настройка `ad_link`
  осталась запасным значением. Разъезд стоил клиенту дня публикаций: 11.08 он поменял
  в промте сайт на приглашение в телеграм, настройка осталась прежней, и валидация
  браковала каждый пост («нет рекламного блока со ссылкой …»), хотя блок был на месте.
  Ссылка ищется ТОЛЬКО внутри блока между рядами дефисов: выше по промту тот же адрес
  упоминается в пояснении, и поиск по первому вхождению ломал `adBlockFromPrompt`
  (страховка «дописать забытый блок» на живом промте не срабатывала ни разу).
- **Рекламный блок клиента чистить нельзя.** В нём есть «— он принес нам», и общее правило
  «убрать тире внутри предложений» ломало фразу заказчика. Блок между строками `----`
  освобождён от чистки, кроме markdown.

## Журнал ошибок: что чинилось и почему (август)

- **Чистка текста и проверка на markdown должны совпадать.** Проверка ловит любое `**`,
  любой `[текст](…)` и решётки заголовка, а чистка снимала только парные `**…**` в одной
  строке и только ссылки с `http`. Модель выделяет «**Итог:» и закрывает строкой ниже —
  символы оставались, пост уходил в брак. Теперь остатки `**` снимаются в любом виде,
  а ссылка разбирается с любым адресом (`vk.com/club1`, якорь `#itog`). Правило: всё,
  на что ругается `validatePost`, должно вычищаться `cleanPostText`.
- **Материал, забракованный дважды, снимается с очереди** (`GIVE_UP_AFTER`). Забракованный
  пост тему не занимает, поэтому неудачный материал возвращался каждый день, жёг по три
  генерации и клал в журнал одну и ту же ошибку («Mailbox Quarantine Alert» — 13, 14 и
  15 августа). Теперь после второго провала материал уходит в «Отклонённые» с причиной.
- **Текст забракованного поста сохраняется** (`posts.createFailed`). Без него разбор
  жалобы «каждый день одна и та же ошибка» упирается в то, что смотреть не на что.
- **Отказ генератора обложек по контент-политике — повод повторить, а не терять слот.**
  Тема проекта для OpenAI пограничная, отказ прилетал почти ежедневно, и оплаченный
  текст оставался без картинки. Повтор идёт один раз с обезличенной темой.
- **Сбой поиска материала ставит поиск на паузу** (6 часов на кредитах, 30 минут на
  зависании). Кредиты кончаются сразу для всех слотов, а таймаут в три минуты на слот
  растягивал прогон на часы.

## Заглушка kie.ai (этап 5)

Живая проверка обложки стоит кредиты и минуту ожидания, поэтому сбойные сценарии гоняются
на локальной заглушке. В dev подставить в `.env`:

```env
KIE_BASE_URL=http://127.0.0.1:3000/_debug/kie
```

Режим — сегментом пути (клиент дописывает `/jobs/createTask` к baseUrl):

| Путь | Что проверяет |
|---|---|
| `/_debug/kie` | нормальный цикл: задача → поллинг → PNG в `/media` |
| `/_debug/kie/nocredit` | `/chat/credit` отдаёт 0 → понятная ошибка вместо 402 в цикле |
| `/_debug/kie/hang1` | первый запрос не отвечает: таймаут и повтор |
| `/_debug/kie/fail2` | 503 на создании задачи, ретраи с бэкоффом |
| `/_debug/kie/taskfail` | задача создана и провалилась (`failMsg`) |
| `/_debug/kie/slowtask` | задача вечно `generating` — общий таймаут ожидания |

Для теста таймаута заодно снизить `KIE_TIMEOUT_MS` (иначе ждать по минуте на попытку).
Перед сдачей вернуть `KIE_BASE_URL=https://api.kie.ai/api/v1` и `KIE_TIMEOUT_MS=60000`.

Грабли, найденные на этапе 5:
- **`controller.abort(new Error(...))` не даёт `AbortError`.** В Node 22 fetch отдаёт наш
  reason, у него `name === 'Error'`, и таймаут писался в лог как «сетевая ошибка».
  В `http-client` заведён отдельный флаг `timedOut`.
- **Провалившуюся задачу нельзя оставлять в `image_task_id`.** Логика «есть задача без
  картинки → дочитать её» на мёртвой задаче зацикливается: каждая новая попытка снова
  читает провал. Чистим id только при окончательном провале (`taskDead`), при таймауте —
  сохраняем: задача оплачена и результат ещё может появиться.
- **`/media` раздаётся без авторизации, и это осознанно**: postmypost скачивает картинку
  сам, по URL, cookie у него нет. Отсутствующий файл при этом должен отдавать 404, а не
  проваливаться в панель и получать редирект на форму входа.
- **Цена обложки зависит от разрешения**: 2K — 10 кредитов, 1K — 6. По решению заказчика
  работаем в **1K** (`kie_resolution` в настройках): в ленте ВК разница не видна.
  При 1080 кредитах это порядка 180 обложек. `aspect_ratio` всё равно задаём явно —
  `auto` тоже даёт 1K, но формат картинки становится непредсказуемым.
- Плейсхолдеры промта обложки: `{{тема}}` и `{{заголовок}}`. Если ни один не встретился
  в тексте промта, тема дописывается отдельной строкой — забытые скобки не должны молча
  превращаться в картинку «ни о чём».

## Заглушка postmypost (этап 6)

Живая проверка публикации создаёт настоящие черновики в проекте клиента, а сбойные
сценарии там не воспроизвести вообще. В dev подставить в `.env`:

```env
POSTMYPOST_BASE_URL=http://127.0.0.1:3000/_debug/pmp
```

Режим — сегментом пути (клиент дописывает `/upload/init` к baseUrl):

| Путь | Что проверяет |
|---|---|
| `/_debug/pmp` | нормальный цикл: 2 группы ВК → одна заливка → две публикации |
| `/_debug/pmp/badaccount` | `connection_status = 0` — понятная ошибка до публикации |
| `/_debug/pmp/noaccounts` | группа есть в БД, но исчезла из postmypost |
| `/_debug/pmp/uploadfail` | загрузка картинки завершилась ошибкой (`status 2`) |
| `/_debug/pmp/slowupload` | загрузка вечно в работе — общий таймаут |
| `/_debug/pmp/fail1` | 503 на `/upload/init`, повтор с бэкоффом |
| `/_debug/pmp/pubfail` | 422 на создании публикации |
| `/_debug/pmp/delete422` | известный баг: 422 при фактически успешном удалении |
| `/_debug/pmp/vklink` | публикация отдаёт адрес записи на стене (кнопка «Найти ссылку») |

Для теста таймаута снизить `pmp_upload_wait_ms` в настройках.
Перед сдачей вернуть `POSTMYPOST_BASE_URL=https://api.postmypost.io/v4.1`.

**Живая проверка из dev требует публичного адреса**: postmypost скачивает картинку сам,
`localhost` ему недоступен. Быстрый туннель (cloudflared уже установлен):

```bash
"/c/Program Files (x86)/cloudflared/cloudflared" tunnel --url http://localhost:3000
# из вывода взять https://<...>.trycloudflare.com и положить в PUBLIC_BASE_URL, затем
docker compose up -d
```

Публичный URL обложки собирается из `PUBLIC_BASE_URL` **на лету** (`publicUrlFor`),
а не берётся из `posts.image_url` — поэтому смена адреса лечит и уже сгенерированные посты.

Грабли, найденные на этапе 6:
- **Живой API отдаёт `{"data": [...], "pages": {...}}`, а не голый массив**, хотя справочник
  обещает массив. Без разворачивания `data` список групп ВК выглядел пустым («Групп ВК
  из postmypost: 0») при трёх подключённых.
- **Типы id проверяются строго.** `account_ids` и `file_ids` из БД приходят строками
  (`bigint` в node-pg отдаётся строкой), и API отбивает их: `422 Validation error in field
  'account_ids.0': Value expected to be 'integer', but 'string' given`. Приводим к числу
  в клиенте. Та же грабля в панели: `publications.id` — `bigserial`, и `item.id === id`
  со числом из URL не сходится никогда.
- **`POST /publications` не ретраится намеренно.** Повтор после фактически созданной
  публикации — второй пост в группе, это видят подписчики. Ретраятся только GET и `/upload/*`.
- **`post_at` округляется до минуты.** Запросили `15:38:57` — в postmypost `15:38:00`.
  Оффсет `+03:00` обязателен: `toISOString()` даёт UTC и уводит время на три часа назад.
- **Картинка заливается один раз на пост**: `file_id` живёт в проекте, сохраняется
  в `publications.pmp_file_id` и переиспользуется всеми группами и повторными попытками.
  postmypost при этом копирует файл к себе на `ycs-media.postmypost.io`.

## Группы ВК (этап 7)

Раздел «Группы» — единственное место, где клиент управляет постингом по группам.
Что важно знать про его устройство:

- **Удаление мягкое** (`groups.deleted_at`). Физический `DELETE` по `groups` унёс бы историю
  публикаций, поэтому «Убрать из списка» только скрывает группу; вернуть её можно кнопкой.
  С этапа 7 жёсткое удаление запрещено и на уровне схемы: FK `publications.group_id`
  переведён с `ON DELETE CASCADE` на `ON DELETE RESTRICT`.
- **Синхронизация не возвращает скрытые группы.** Иначе «удаление» отменялось бы первым же
  нажатием «Обновить список». В сводке синхронизации такие группы считаются отдельно
  («скрытых N»).
- **Синхронизация не сбрасывает `posts_per_day`.** Значение задаёт клиент; `upsertFromPmp`
  пишет его только при вставке новой группы (из настройки `default_posts_per_day`).
- **`posts_per_day` работает уже сейчас**, не дожидаясь планировщика (этап 8): `publishPost`
  считает успешные публикации группы за сегодня по МСК и отказывает сверх лимита. Повторная
  публикация того же поста в ту же группу лимит не расходует (обновляется существующая строка
  `publications`, а не создаётся новая).
- **Выключенная группа не получает посты** ни в прогоне (`listActive`), ни при явном выборе
  в форме публикации — проверка стоит в сервисе, а не только в разметке.

## Соцсети (ВК и Одноклассники)

- **Список площадок задан в одном месте** — `NETWORKS` в `lib/postmypost.js` (`chanel_id`
  2 = ВКонтакте, 5 = Одноклассники). Всё остальное про соцсеть не знает: раздача тем идёт
  по группам, лимиты и слоты считаются на группу, публикация в postmypost одинаковая для
  всех площадок. Новая сеть — строка в `NETWORKS` плюс адрес сообщества в `groupWallUrl`.
- **Группа ОК встаёт в тот же круг раздачи, что и очередная группа ВК**, и получает свои
  темы: пересечений нет (правило «один материал — одна группа» общее). Зеркалирование
  одного поста в две сети — отдельная логика, её нет.
- **`groups.chanel_id`** заполняется синхронизацией из postmypost. Аккаунты сетей вне
  списка (например Telegram) в панель не попадают.
- **Адрес записи ищется по самому адресу**, а не по имени поля: `postUrlFrom` понимает
  и `vk.com/wall-123_456`, и `ok.ru/group/123/topic/456`.
- Новая группа приезжает **выключенной** — постить в неё система начнёт только после
  того, как её включат в панели и зададут «постов в день».

## Прогон и расписание (этап 8)

Прогон устроен как **план в БД**, а не как последовательность вызовов в памяти процесса:
`buildPlan` (`services/plan-run.js`) раскладывает материалы по группам и слотам,
`runCycle` (`services/run-cycle.js`) исполняет слоты по одному.

- **Свежее забирается ДО плана.** `refreshSources` (`services/refresh-sources.js`) обходит
  все включённые источники в начале прогона. До этого сайты перечитывались только при
  нехватке материалов (`backfillArticles`), и на проде вышло двое суток без единого обхода:
  запас в базе был, новое на сайтах старело. Сбой источника прогон не роняет, повторный
  обход одного сайта — не чаще `refresh_sources_min_age_minutes` (60).
- **Без текста материал в очередь не идёт**, поэтому `extract_limit_per_check` — не
  косметика: при 10 у cryptorussia и kaper накопилось по 40 материалов, до которых очередь
  не дошла бы никогда. Сейчас 30, настройка в панели («Обновление источников»).
- **Один материал — одна группа.** Раздача по кругу из общего списка кандидатов; сверх этого
  уникальные индексы `run_items (run_id, article_id)` и `(run_id, post_id)` — пересечение
  физически не вставится. Материалы, занятые незаконченным прогоном, в новый план не берутся.
- **От свежих к старым.** Готовые посты и материалы под генерацию сливаются в один список
  и сортируются по дате материала, поэтому порядок внутри группы монотонный.
- **Очередь источников (`sources.priority`) сильнее даты.** Меньше число — раньше берём
  темы сайта; в панели это селект «берём первым / обычная очередь / берём последним»
  (10 / 100 / 900). Сортировка по дате внутри очереди сохраняется. Приоритет стоит перед
  датой намеренно: cryptorussia публикует чаще остальных, и при общей сортировке по дате
  план забирала она одна. Учитывается и в SQL-выборке кандидатов (там стоит `LIMIT`
  по ёмкости прогона), и при сортировке кандидатов в `buildPlan`.
- **Слоты времени** считает `lib/schedule.js`: равномерно внутри окна
  `posting_window_start`-`posting_window_end` плюс джиттер до `slot_jitter_minutes`, минуты
  не повторяются (postmypost округляет `post_at` до минуты). Окно на сегодня закрылось —
  прогон переносится в завтрашнее окно целиком.
- **Сбой прогона не должен стоить суток.** Планировщик считает запуск удавшимся в момент
  старта, а прогон падает в фоне минутой позже — и в ежедневном режиме следующая попытка
  была бы только завтра. 02 и 03 августа так пропали два дня подряд: прогон падал на записи
  плана. Поэтому упавший прогон повторяется через `scheduler_retry_minutes`, до трёх раз
  (`failedCyclesInRow`, окно 12 часов). «Нет материалов», «дневные лимиты», «нет групп» —
  не сбой: повторять нечего.
- **Падение фонового прогона отмечается временем** (`lastBackgroundFailureAt`). Прогон,
  упавший ДО `startRun`, не сдвигает точку отсчёта расписания, и без этой отметки запуск
  повторялся бы каждую минуту вместе с обходом сайтов.
- **План пишется одной вставкой, поэтому его отбитие роняет прогон целиком.** Уникальный
  индекс `run_items (run_id, article_id)` отбил план, в котором оказались два готовых поста
  по одному материалу (#5 и #6 по merabo, оба из ручных проверок — очередь такого не
  запрещает). Кандидаты дедуплицируются по материалу в `buildPlan`, до вставки.
- **Прогон, застрявший в `running`, держит якорь расписания** и в панели выглядит рабочим.
  `closeStaleRunning` закрывает такие: старше двух часов и без единого слота в
  `planned`/`generated` (у живого прогона слот в работе есть всегда).
- **Второй прогон отклоняется, а не ждёт.** Advisory lock Postgres (`withAdvisoryLock`,
  ключ 815240801) на отдельном соединении: упавший процесс не оставляет вечный лок.
- **Прерванный прогон продолжается.** `runs.unfinishedCycle()` находит прогон со слотами
  в статусах `planned`/`generated`, и следующий запуск доделывает именно его. Уже
  опубликованные слоты повторно не уходят, уже сгенерированный текст заново не создаётся.
- **Время местное.** Контейнер в `Europe/Moscow`, поэтому в расписании обычные
  `new Date()`/`getHours()`. Явный `+03:00` нужен только на границе с postmypost.

Ручной запуск — кнопка «Запустить прогон» на «Обзоре» (там же план и итог последнего
прогона). Автозапуск по расписанию — этап 9; `nextRunAt` уже считает время по настройкам.

## Наблюдаемость (этап 11)

- **Сбои пишутся в `app_errors`** — раздел «Ошибки» в панели. Запись делает
  `services/capture-error.js`: сервис, HTTP-статус, адрес и **тело ответа** он достаёт
  из `HttpError` по цепочке `cause`, а `request-id` и `run_id` — из сквозного контекста.
  Поэтому у ошибок клиентов провайдеров (`PmpError`, `KieError`, `OpenRouterError`)
  обязательно проставляется `cause`: без него в журнал не попадает ни адрес, ни тело.
- **Одна ошибка — одна запись.** Тот, кто поймал сбой ближе к месту, ставит на объекте
  ошибки `captured = true`; вызывающий (слот прогона, фоновый прогон) видит пометку
  и второй, более бедной записи не делает.
- **`request-id` — ключ к логам.** Он показан в панели у прогона, публикации и каждой
  ошибки; строки события ищутся как `docker compose logs app | grep <rid>`.
  У ручного прогона это тот же id, что у HTTP-запроса кнопки.
- **Ссылки на пост в ВК у черновика не существует** — postmypost отдаёт адрес записи
  только после реальной публикации. В логе публикаций ссылка ведёт на группу,
  а адрес поста подтягивается кнопкой «Найти ссылку» (`GET /publications/{id}`,
  адрес ищется по шаблону `vk.com/wall…` в ответе — имени поля в справочнике нет).

## Сбор материала поиском (этап 13)

- У scama.net и all-comment своих текстов нет — только названия проектов. Такая тема
  идёт в генерацию через `services/research.js`: firecrawl `POST /search` со
  `scrapeOptions` отдаёт выдачу сразу с markdown, из неё собирается материал.
- **Главный фильтр — релевантность, а не наличие текста.** Поисковик всегда что-нибудь
  вернёт: по неизвестному проекту приходят общие статьи «как распознать мошенников»
  (РБК, Т—Ж, YouTube). Отдать их модели хуже, чем не искать вовсе — она перенесёт
  в пост чужие лицензии, страны и суммы, и получится убедительная выдумка.
  Проверено на живой выдаче: так в пост про `merabo.ru` попала регистрация в Аргентине.
- **Опознаём по домену, а не по слову.** «merabo» дало индийскую Merabo Labs;
  домен `merabo.ru` — признак однозначный, ему хватает одного упоминания,
  отдельному слову названия нужно два.
- **Имя проекта для поиска и для проверки поста считается по-разному.**
  `projectSearchName` сохраняет домен (искать надо «merabo.ru»), `projectDisplayName`
  и `projectTokens` его срезают (для сверки дублей «atlascapital.com» = «atlascapital»).
- Ничего не нашлось — не беда: пост пишется по теме, как раньше. Сбой firecrawl уходит
  в журнал «Ошибки» шагом «сбор материала» и прогон не роняет.
- Настройки в панели: режим (`off` / `missing` / `always`), число страниц, символов
  со страницы, шаблон запроса с `{{проект}}`. Лимит firecrawl — 1000 запросов в месяц
  на проект, поэтому число страниц настраивается, а не зашито.

## Прод (общий сервер okhost)

> Дальше по разделу местами описан прод ПЕРВОГО клиента — выделенный VPS со своими
> Postgres и Caddy. Для этого проекта верно другое, см. навык `/okdeploy2`:

- Сервер `193.17.95.54` (okhost, общий на несколько клиентов), каталог
  `/opt/projects/komarov-vkposter`, домен `vktop545.com` (A-запись уже на этот IP).
- **Свой Postgres, свой Redis и свой Caddy проект не поднимает** — они общие серверные.
  Подключение к БД приходит из `/opt/projects/komarov-vkposter/.env.infra` (`DATABASE_URL`),
  HTTPS выдаёт общий Caddy командой `okhost web komarov-vkposter vktop545.com 3000`.
- **Никаких `ports:` в compose** — docker пробивает UFW насквозь, опубликованный порт
  окажется в интернете в обход фаервола. Наружу только через Caddy.
- Контейнер строго `komarov-vkposter-app` (на это имя ссылается Caddy), `mem_limit` обязателен:
  без потолка потёкший проект уронит соседей по серверу.
- Управление — CLI `okhost` на сервере: `okhost logs|rebuild|psql|ps|env <проект>`.
- Ключ доступа к серверу лежит в самом навыке: `~/.claude/skills/okdeploy2/.secrets/infra_key`.
- Репозиторий `https://github.com/dimatolpygin/vkposter-komarov-`. Ветка разработки `dev`,
  ветка выката `master`. **Пуш в `master` = выкат на прод**, поэтому только по указанию.

```bash
# прод запускается ДВУМЯ файлами, dev-овский override не подхватывать
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build
# то же самое, но правильным способом — с ожиданием /health и подстановкой версии
./deploy/deploy.sh          # выкатить то, что лежит в каталоге
./deploy/deploy.sh --pull   # подтянуть origin/master и выкатить
./scripts/install.sh        # первичная подготовка сервера, идемпотентно
```

- **`ports` в compose-файлах СКЛАДЫВАЮТСЯ, а не заменяются.** Поэтому публикация порта
  живёт не в базовом файле, а в `docker-compose.override.yml` (dev, `0.0.0.0:3000`) и
  `docker-compose.prod.yml` (прод, только `127.0.0.1:3000` — наружу ходит Caddy).
  Правило в базовом файле давало «address already in use» на пустом сервере.
- **Бит запуска у `.sh` хранится в git** (`git update-index --chmod=+x`). Файл, созданный
  на Windows, приезжает как `644`, а `git reset --hard` в выкате отменяет `chmod` на сервере —
  cron-бэкап после первого же деплоя падал бы с «Permission denied».
- HTTPS делает Caddy (`deploy/Caddyfile`), сертификат Let's Encrypt выпускается сам;
  тома `caddy_data`/`caddy_config` обязательны — без них сертификат перевыпускается
  при каждом пересоздании контейнера и упирается в недельный лимит.
- Версия выката видна в подвале панели (`APP_REVISION` — короткий хеш, подставляет
  `deploy/deploy.sh`). Локально переменной нет, строка не показывается.
- Бэкап базы: `deploy/backup-db.sh`, cron `/etc/cron.d/vkposter-backup` в 03:30 МСК,
  дампы в `/opt/vkposter/backups`, хранение 14 дней, лог `/var/log/vkposter-backup.log`.
- После перезагрузки сервера стек поднимается сам (`restart: unless-stopped` + docker в systemd),
  миграции применяются на старте приложения.
- На проде `NODE_ENV=production` → отладочные роуты `/_debug/*` не подключаются,
  заглушки провайдеров недоступны. Все ключи в `.env` боевые.
